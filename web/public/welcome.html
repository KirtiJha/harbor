The problem

localhost turns into a crowded harbor

Every project brings a dev server, an API, a database and a watcher. They pile up on ports you never chose, and the tools to see them are a wall of lsof output.

Error: listen EADDRINUSE: address already in use :::5173

“Port already in use”, by what?

Something holds the port. Finding out what means lsof -i :5173, reading a pid, then ps to see what that pid is.

VITE ready → http://localhost:5174/ Port 5173 is in use, trying another one…

Apps quietly move ports

Vite and Next take the next free port without asking. The bookmark on :5173 now opens a different project.

$ kill 55958 [vite] restarting… listening on :5174

Killing the wrong process

The pid on the port is a child. Its parent (make dev, npm run dev, a reloader) starts it again.

node 62826 *:4700 (LISTEN) # reachable from the café Wi-Fi

Exposed and forgotten

Servers bound to all interfaces are open to your network. Week-old servers keep holding memory nobody uses.

How it works

One loop, from sockets to your screen

A small local server reads the machine every two seconds, makes sense of what it finds and streams the picture to your browser. The flow below is live: hover a box.

  1. Read the machine: every listening TCP socket (lsof, or netstat on Windows) and the whole process table (ps, or PowerShell). About 0.2 s.
  2. Understand each one: its project (package.json, pyproject, git), its framework (Vite, Next, Uvicorn, Postgres…) and the app that launched it.
  3. Ask each server over HTTP for its status, page title and response time, so “node” becomes “Shop web · 200 · 7 ms”.
  4. Decide: what opened or closed, what is idle, what moved off its port, what is exposed to the network, what is safe to stop.
  5. Stream the picture to the browser as it changes (server-sent events), with every action behind a session token.
  6. Run your saved apps with their output captured, conflicts resolved and crashes restarted, and remember notes and settings.
  7. Route http://shop.localhost:7475 to wherever Shop is listening today, websockets included.
Stop whole app

Stops what started it, not just the process on the port

The process on the port is rarely the one you meant. Porthaven walks up the process tree through launchers (make, npm, shells running a command, reloaders) and stops at your terminal, editor or agent. It never goes past them.

Then it asks politely (SIGTERM), waits a few seconds, and forces only the processes still running (SIGKILL). Desktop apps and system services need you to type the port number first, and Porthaven never uses sudo.

Stable names

Bookmarks that keep working when the port changes

Give an app a short name and open http://name.localhost:7475. Porthaven sends it to whatever port the app is on now, websockets and hot reload included. When Shop lands on :5174 because Docs site got :5173 first, the bookmark still works.

Browsers send *.localhost to your own machine. No DNS setup, no hosts file, no certificates.

Command line

The same answers in your terminal

Every dashboard question has a short command. who tells you what is on a port, kill --app stops it properly, and free finds a port you can use.

  • porthaven ls listening ports (--all, --json)
  • porthaven who 5173 command, folder, app, HTTP answer
  • porthaven kill 5173 --app stop the whole app
  • porthaven free 3000 -n 5 next free ports
  • porthaven service install start at login

        Safe by design
        
A process killer you can trust

      

      

        
127.0.0.1 only
Porthaven never listens on your network.

        
No DNS rebinding
It answers only requests addressed to its own localhost port.

        
Session token
Every change needs a token only Porthaven's own page can read, so other sites can't send it commands.

        
Guard rails
It can't stop itself, other users' processes, or anything outside what it shows. Desktop apps and system services need you to type the port number.

        
No sudo, no cloud
Your user's processes only. State stays in ~/.porthaven.

        
Zero dependencies
The backend is the Python standard library, so there's nothing to install or audit.
